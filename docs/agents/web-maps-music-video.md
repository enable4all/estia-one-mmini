# Web search, places, music, YouTube links and chords

## Layout

- `fetcher` (guarded web fetch; its 30 s in total is enforced on the whole request, `fetcher._Cut`: a timer shuts the connection down at the deadline, through a second handle of the socket, as TLS takes the first one over)
- `video` (YouTube links: the strict link check, the YouTube helper run, a long video's parts and code's note before them, the last video kept in memory per account for 10 minutes, the check that her answer never copies the captions)
- `theory` ([chords]: the chord arithmetic, four pure functions with a fixed input and one frozen result out, `transpose`, `capo`, `notes`, `key`, each result with its `spoken` form for a call; `read` and `chord_of`, the one chord parser the tool and the check share; `parse_key` and `keys_in`, keys in words in 11 languages; standard library only, no network, files or programs; every rule is the chords rule book's, S1 to G3, kept outside the repo with the design)
- `chords` ([chords]: Gemma's `chords` tool around theory, `ChordTool` and its `Result` (code's fixed lines, the spoken line, the chords in and out, the page that holds them); `note` and `spoken`; `read`, the reader of chords in her words with her voice's context rules (ChordSpeller's for English, ChordWords' for the ten others, the packs' music words and joins: `MUSIC_WORDS`, `JOINS`, test-checked against the Swift packs; known gap: it keeps the gaps, marks and forms of before the chord speech fixes of 18 Oct, so a chord after ";", a spaced slash, "…", "‖", "⏸" or a mark, an "A D E A" row, "C-7" and a bracket's alterations are not checked); `check`, the reply check)
- `spotify_auth` (PKCE paste sign-in, tokens), `spotify` (Web API client), `soundtouch` (wake a Bose), `music_tools` (what Gemma's music tools do)
- `web_search` (Ollama web search, Brave as backup; counters, pauses)
- `maps` (the front: Google Places and Routes first once its key is set up, else OpenStreetMap; location pins, the home area), `osm` (OpenStreetMap's free services: Nominatim for places and lookups, FOSSGIS's OSRM servers for walk, bike and car, Transitous for public transport), `osm_hours` (OpenStreetMap's `opening_hours`, common forms only), `map_data` (Place, Route, MapsError, shared by both)
- `tools/youtube/`: the YouTube helper (youtube-transcript-api in its own uv environment; the captions of one video by its ID, from www.youtube.com only).

## Commands

- Web search keys (from the login keychain into `web.env`, 0600, lengths only): `scripts/set-web-keys.sh` (the person runs it in their own Terminal window: it may ask for the login password, and in her own user for the Mac password) Doctor's Web search line without a key is a "!", never a ✗ (on by default, and setup lets the key wait: review docs-default-web-pick-leaves-x), its fix the way that asks for the key itself: `DOCTOR_WEB_KEY_FIX` (`scripts/setup.sh --extras`), in her own user `DOCTOR_WEB_KEY_FIX_OWN` (`estia secret set web.env OLLAMA_API_KEY`); `scripts/set-web-keys.sh` needs the key in the login keychain first.
- YouTube helper: `cd tools/youtube && uv run pytest -q && uv run mypy` (recorded responses, no network)

## Rules

- YouTube links (`video`, `tools/youtube`): always on with read_link (no switch). Only a link in the user's current message is read (`video.video_id`: youtube.com, www., m. (watch, shorts, live, embed), music. (watch) and youtu.be; no login, port or other host; exactly one `v=` whose raw value is the ID), and only its 11-character ID reaches the helper, never the link; a video found by web search is named, never read. The helper (youtube-transcript-api 1.2.4 pinned, its requests stack in `uv.lock`) runs with fixed argv (`captions --until 7200 -- <ID>`: the ID last, after `--`, since about 1 in 64 IDs starts with `-`; the fake helper reads its argv with the real parser's shape), no shell, a clean environment; it asks only https://www.youtube.com (every request and redirect through `GuardedAdapter`, at most 3 redirects), with no proxy settings, .netrc, cookie file or account (`trust_env` off; the session lives for one run), stops itself after 20 s (the bridge kills it at `youtube_helper_timeout`, 30 s) and prints one JSON line: manual captions before auto-generated ones, each in the video's own language first (the auto-generated track's language, else the track YouTube shows by default, else English, then YouTube's order, which goes by language name: live, an English lecture without an auto-generated track first came back in Arabic; so a hand-written track in another language, often a translation, beats YouTube's automatic one in the video's own language), never YouTube's machine translation; or an error code, never YouTube's or the library's own error text. Nothing is transcribed (no yt-dlp, no Whisper): no captions is "This video has no captions." Captions are outside text, cleaned per segment as a page is (`video._captions`: no chat-template token or hidden character, review I9), with a page's flags (no remember or forget, no reminders, device changes wait for a yes, links defanged; the user's own video link stays tappable, `Turn.allowed_links`: `video.link_in`, the link as the user's message has it, never Gemma's argument, which a planted line could make carry another link) and never stored: no document, the tool log keeps `prompts.VIDEO_STUB`, learn_link and `/learn` refuse video links. At most 2 hours are read (`CAP_SECONDS`; a longer video's first 2 hours, said in code's note and in the result), and at most `CAP_CHARS` (120,000 characters; the helper's `MAX_CHARS` is the same, and it says `cut_by`): captions cut by size get their own words (`VIDEO_READING_SIZE`, `VIDEO_CUT_SIZE`: "the first 1 h 10 min of a …"), never "2 hours". Captions over `PART_CHARS` (15,000) are split into even parts of whole lines (a line about every 30 s, or sooner at `LINE_CHARS`, 2,000; no part over `PART_CHARS`: a part closes early, and a longer line is cut with its time on each piece): code's note goes first (`video.reading_note`, "Reading a 1 h 40 min video: about 1 minute.", in place of the busy note; `PART_SECONDS` from the evals: about 5 s a part on the M6 mini), then Gemma notes each part in a call of its own (no tools, the user's message in each) and her answer joins the notes. A second read_link of the same video in one answer reads nothing again (`Turn.videos_read`, `prompts.VIDEO_READ_ABOVE`: no part calls, no second note). The answer gives times for the main points, says when the captions were auto-generated and is capped by `reply_max_tokens` (600). It never holds the captions word for word, in code: `brain._without_captions` (`video.without_copies`) leaves out each sentence of hers holding 13 caption words in a row (case and punctuation aside, also across sentences; Chinese, Japanese and Thai by character), and, when runs of 6 or more hold more than 30% of the captions' words, every sentence with one; then code's line `prompts.VIDEO_NOT_SENT` gives the user's link. Asked for the full transcript, the prompt has her give the link. The last video's captions stay in memory per account and conversation for 10 minutes (`KeptVideos`; a timer drops them, `/new` too), never on disk: read_link with that video's link (any of its forms) reads them again without the helper, and while they are kept code's line `prompts.VIDEO_KEPT` (the link and the minutes left) is last in her prompt (live evals: without it she answered follow-ups from her own summary). When the user's current message holds a YouTube link (`video.first_link`, as `link_in` finds it), code's line `prompts.VIDEO_IN_MESSAGE` follows, last (read_link reads that video's captions; asked for the full transcript, the link, which opens the video: never called the transcript); a message without one gets no line and its request stays byte for byte as before (`test_without_a_youtube_link_her_request_is_the_one_from_before`; every non-video eval case's first request matched fa95b51's). read_link's description never names YouTube (see Gotchas). Never on a call (a link cannot be spoken; no line there either). Logs hold codes, character counts and times, never the ID or a title. `status.json`'s `youtube` part (always shown): a video without captions, unavailable or age-restricted is YouTube answering (working); a block is `refused`, no answer `no_answer`, a changed YouTube `bad_answer`; doctor reads the library's version from its files (no network) and warns when the helper is missing (in her own user its fix is the deploy, `prompts.DOCTOR_YOUTUBE_DEPLOY_FIX`; her own words name no command, `VIDEO_ERRORS["helper_missing"]` points to doctor). YouTube's terms forbid automated access: accepted by the owner for personal use (SECURITY.md, known gaps).

## Gotchas

- "See Gotchas" in the YouTube and Chords rules: a tool's description is in every request (it cost call_goodbye 30 points), in `docs/agents/prompts-evals.md`, Gotchas.
- A socket timeout bounds each read, never the whole request: a site that sends its status line, headers, chunk lines or TLS handshake a byte at a time (Python's http.client reads them with no deadline) held a worker thread for as long as it dripped, and `App._fetch`'s `wait_for` ends only the wait, never the thread (review I36; the default pool is shared with Gemma's chat). A shut socket can read as the end of the headers: a fetch cut off is "too slow", never a page. Name resolution (`getaddrinfo`) is not cut: the system's DNS timeouts bound it.
- A helper the bridge runs with `python -I` (`tools/youtube` too): see `docs/agents/devices.md`, Gotchas.
