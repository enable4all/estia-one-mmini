# Set up Estia with your AI

This file is written for an AI coding assistant, such as Claude Code or Codex, that a person has asked to install Estia on their Mac. If you are that person: paste `can you help me install this? https://github.com/enable4all/estia-one-mmini` into your AI; or, in Terminal, run `git clone https://github.com/enable4all/estia-one-mmini.git ~/estia` (a Mac without Apple's Command Line Tools asks to install them first, in a box on the Mac's own screen: say yes, wait, then run the clone again), then open your assistant in `~/estia` and say "set me up". It checks the Mac, starts setup and says what each screen needs. Every answer is yours: typed in the Estia Setup window on the Mac's screen, the Mac password only in macOS's own box, never in the chat.

---

## For the AI: your job

You are helping one person install Estia, a private AI thinking partner, on their own Mac. She is called Estia unless they give her another name (`name` in the config, 1 to 20 letters, spaces or hyphens); use the name they chose from then on.

- **Estia is reached only through Signal.** There is no web app, no port reachable from other machines and no cloud AI: the bridge opens no port, and Ollama and her voice service listen only on the Mac itself.
- **The model runs on the Mac.** A cloud model, which Ollama runs on its own servers, is refused. Mail and the calendar are read-only.
- **Only the owner's Signal account gets answers.**

Your job is to keep it that way while you help. You check the Mac, start setup, follow its step lines and say what comes next; the person answers every question in setup's own window.

**Asked with only the link** ("can you help me install this?" and this repository's address): first ask how they want to run it, in two sentences: you drive it (in Terminal on that Mac: the clone, the checks in 1 and setup in 2, saying what each screen needs while they type the password and codes), or they run it and you help when something stalls. Offer to drive it only with a command tool on that Mac, at its own screen; without one, they run every command.

**Two routes.** At the Mac's own screen, you start `scripts/setup.sh` yourself (2, Claude Code first): the Estia Setup window opens there and asks everything, and your command reads only setup's step lines, never an answer. Over a remote login (SSH), inside screen, tmux or herdr, or when your command tool gives programs a terminal of their own, the person runs setup in their own Terminal window (4). Either way the questions, their words and their order are setup's own: read them in the source (3), never from this file.

**You may run only these** (read-only or the person's own folders; admin rights only through macOS's own box in setup's window, where the person types the password): `git clone https://github.com/enable4all/estia-one-mmini.git ~/estia` (only when `~/estia` does not exist yet), the checks in 1, `scripts/setup.sh --dry-run`, `scripts/setup.sh --extras --dry-run`, `scripts/doctor.sh` (before the move), `scripts/harden.sh --dry-run`, `scripts/migrate-to-own-user.sh --dry-run`, `scripts/share-documents.sh --dry-run` and `scripts/share-documents.sh` (6, Documents), `scripts/install-ollama.sh --dry-run`, `(cd tools/youtube && uv sync --frozen)`, and, at the Mac's own screen only, `scripts/setup.sh` with no other option (2). Read `~/.config/estia-setup/ai-run.log` (setup's step lines only). Never open setup's answers file, `~/.config/estia-setup/answers.toml`: it holds About you, the home area, her number and her Account ID; ask the person. Never prepare an answers file for `--answers`: setup refuses it when you start setup. The person runs everything else that needs admin rights: every command that starts with `/usr/bin/sudo`, and every script that calls it (rule 3).

**Done when:** `/usr/bin/sudo /usr/local/estia/bin/estia doctor`, run by the person, shows no ✗ and her welcome message has arrived on the person's phone. They reply to it to see her answer.

## The rules (security comes first)

1. **Never ask for, accept or repeat a secret in the chat:** API keys, passwords, tokens, the Signal captcha link, the SMS code, the Registration Lock PIN, the Recovery key of an account without a number, the calendar's secret address, app-specific passwords, the TP-Link login, and any sign-in code or address a script asks the person to type or paste (Microsoft's device code, gcloud's codes, the address Spotify's sign-in ends on). Each goes into a field of the Estia Setup window, a hidden prompt in the person's own Terminal, or their own browser: never on screen, never on a program's command line, never in a file you can read. A secret pasted into the chat anyway has left the Mac, to your company's servers: tell them so, and to replace it at its service (a new key, the old one deleted; a new Mac password in System Settings → Users and Groups; a new Registration Lock PIN with `scripts/harden.sh --new-pin`; a new secret address of the calendar); a one-time code or captcha link already used is spent. A Recovery key pasted into the chat cannot be replaced, and whoever reads it can take the account over: tell them to make a new account without a number and move her to it with `/usr/bin/sudo /usr/local/estia/bin/estia signal-login` (on a clean Mac), then stop using the old one.
2. **Never print or read secret files:** `~/.config/local-assistant/config.toml` (except to check that it exists), `*.env`, `*tokens*.json`, the answers file above, the login keychain, `/private/var/run/estia-setup.*` (setup's admin steps: never list, open or read them), and nothing under `/var/estia` (her home: only her own macOS account can read it, and you must not try). Use the doctor: it prints only ✓/✗ and the lengths of keys, never their values.
3. **Never run `sudo` yourself, and never type, see or ask for the Mac password.** Admin rights come only from the person: macOS's own password box in the setup window ("Estia Setup wants to make changes."), or sudo in their own Terminal window (a Claude Code `!` command has no terminal for the password). The scripts that call sudo themselves once she runs as `_estia` (`scripts/install-daemon.sh`, `scripts/install-voice-daemon.sh`, `scripts/set-web-keys.sh`, `scripts/set-calendar-url.sh`, `scripts/set-calendar-password.sh`, `scripts/set-tapo-credentials.sh`, `scripts/mail-login.sh`, `scripts/spotify-login.sh`, `scripts/hue-pair.sh`, `scripts/tapo-discover.sh`), and `scripts/install-ollama.sh`, are the person's to run in their own Terminal window, or setup's to run in its window on their Run it.
4. **Name the password box before it comes:** macOS's own box in the window, or sudo's password prompts in Terminal, each with its step's line (3).
5. **Never weaken a safety rule** (AGENTS.md, "Hard rules", and `docs/agents/safety.md`): no extra allowed accounts, no port reachable from other machines (the bridge opens no port), no `--no-verify`, no world-readable files, no cloud model.
6. **Explain each step in one plain sentence before it runs.** Say what it does and what leaves the Mac, in words the person knows: "admin rights", not "sudo"; "only the Mac itself", not "127.0.0.1". Exact terms only in the commands they type.
7. **Never drive their browser or click for them.** Give numbered steps on the service's own page (6); they click, sign in, accept terms and copy.

### The password and paste method (say it once, in these words)

- **The Mac password** goes only into macOS's own box, "Estia Setup wants to make changes.", or, in Terminal, at sudo's own `Password:` prompt. Never into the chat, never into the setup window's fields. I never ask for it and never see it.
- **Codes, PINs, keys, the captcha link, the Account ID and the Recovery key** go only into the setup window's field for them (or Terminal's hidden prompt): copied on the phone or in the browser, pasted there. Nothing typed in the window reaches me: I read only setup's step lines.
- **Anything pasted into this chat leaves the Mac,** to my company's servers. So nothing from the password manager, the phone or a service's page goes into this chat, not even "to check it".
- **What I see:** the Mac's checks, setup's step lines ("Step 2 of 9: her model", "In the window: SMS code [sms_code]", "In macOS's own box: …") and the doctor's ✓/✗ lines. Never an answer.

## 5. After setup

- **A new install has her service; with calls, her voice service too:** on a yes to calls (the recommendation), setup installs her voice service and builds calls, which work once her config has `[voice]` without its `#` and a `[calls]` line (in the setup window, "Her config", Add them adds them for her). Without calls, her voice service comes with `scripts/install-voice-daemon.sh` (6).
- **A first install has no rollback: the move keeps no copy, and her only copy of her data is in `/var/estia`.** A rollback exists only after moving an older install (below).
- **Her welcome** on Signal says what is set up, something to try for each, and what stays on the Mac. The person replies to it; `/help` then lists what she can do in this install.
- **Keep it running.** Tell the person the three settings that decide whether she answers after a power cut or a restart (setup_assistant.md, 2.8):
  - **No sleep, and start after a power failure:** System Settings → Energy, or `/usr/bin/sudo /usr/bin/pmset -a sleep 0 autorestart 1`, run by the person. Doctor's Power line shows ! until both are set.
  - **A MacBook** has no start after a power failure: System Settings → Battery → Options, "Prevent automatic sleeping on power adapter when the display is off", or `/usr/bin/sudo /usr/bin/pmset -c sleep 0` (plugged in), run by the person. Kept plugged in, lid open: a closed lid without an external display still stops her.
  - **Ollama starts with the Mac:** its background service starts at boot without a login, as hers does, so no automatic login is needed (with the Ollama app: she answers only while someone is logged in and the Ollama app runs; automatic login lets anyone at the Mac into their account after a restart).
  - **FileVault:** with it on, someone types the password after each restart. For a planned restart, `/usr/bin/sudo /usr/bin/fdesetup authrestart` skips that prompt.

## 6. Extras with your AI

The extras, in setup's own words (they speak to the person; `scripts/setup.sh --extras --dry-run` lists each in one line once setup has run, and only a summary on a fresh clone):

- `voice`: Voice notes and spoken answers (speech stays on the Mac). Leaves the Mac: nothing (the speech models are downloaded once, from Hugging Face). Needs: about 1.7 GB of disk and your Mac password once.
- `calendar`: Calendars (Google, Outlook, iCloud, Fastmail or Nextcloud) in the morning digest and on request. Leaves the Mac: each calendar, read-only, from its own service: Google, Microsoft, iCloud, Fastmail or Nextcloud. Needs: a Google calendar's secret address, an app-specific password (iCloud, Fastmail, Nextcloud) or the mail extra.
- `mail`: Read-only mail from Microsoft 365 mailboxes, sorted for you. Leaves the Mac: mail is read from Microsoft (Microsoft Graph); bodies are never stored. Needs: a Microsoft 365 mailbox, an app registered in Microsoft's admin site and a Microsoft sign-in.
- `lights`: Lights and plugs at home: Kasa, Tapo and Philips Hue. Leaves the Mac: nothing (they are switched over your home network). Needs: the devices on your home network; newer Kasa and Tapo: the TP-Link login; Hue: the Bridge's button.
- `web`: Web search with sources. Leaves the Mac: your search words, to Ollama's web search (Brave Search as backup). Needs: an API key from your account at ollama.com (and Brave Search's, for the backup).
- `maps`: Places and routes from OpenStreetMap: free, with opening hours where the map has them. Leaves the Mac: the place or route you ask about, to OpenStreetMap's free services; 'near me' is rounded to about 1 km. Needs: nothing.
- `music`: Spotify by text message. Leaves the Mac: play and pause commands, to Spotify. Needs: Spotify Premium, an app on Spotify's developer site and a Spotify sign-in.
- `projects`: Your git projects in one folder of this Mac, read-only: summary, docs or code. Leaves the Mac: nothing (the files are read on the Mac). Needs: a folder of git projects in your home.
- `documents`: Your PDFs and text files in ~/Estia-KB and the ones you send her, read on the Mac. Leaves the Mac: nothing (the files are read on the Mac). Needs: nothing: the share makes ~/Estia-KB.
- `calls`: Voice calls with her, and wake-up calls (needs voice). Leaves the Mac: the calls, through Signal (end-to-end encrypted); the build's code comes from GitHub and crates.io. Needs: voice first and several GB of disk for a long build; no GitHub account.
- `chords`: Chords transposed, moved for a capo, a chord's notes and the key of given chords, worked out on the Mac. Leaves the Mac: nothing (the chords are worked out on the Mac). Needs: nothing.
- `google-maps`: Google Maps for places and routes, asked first: ratings, prices, open now, bus and tram lines. Leaves the Mac: the place or route you ask about, to Google; 'near me' is rounded to about 1 km. Needs: a Google Cloud project with billing, and a Google sign-in (gcloud).

## Security (what to do and what to say)

- **Run setup's security step with them** (`scripts/harden.sh` runs the same step later; `scripts/harden.sh --dry-run` first shows every check and command). Before each sudo prompt or macOS box, say in one sentence what it does: the move creates her own macOS account and copies her data, the security step changes SSH or removes a rule that skipped the password (with `--nuclear` also the firewall), her commands run as her.
- **The Mac's security levels.** The Mac's security has two levels: hardened, set by the security step (`scripts/harden.sh`), and nuclear, the hardened level with the Mac's firewall on and python3 and ruby off its list (`scripts/harden.sh --nuclear`; its stealth mode and keychain lock do not count toward the level). Doctor names the level the Mac is at. The nuclear level, only for deeply technical users and best on a Mac used for Estia alone: the Mac's firewall on, with each program that other machines reach asked about one by one; python3 and ruby off its list; stealth mode and the keychain lock, each asked first. Outgoing connections and remote login (SSH) are never blocked, nor are signed programs while macOS's own setting lets signed software through (as on a new Mac). The nuclear option is never part of setup: it may stop other services on this Mac (it says how first). Offer it only to a deeply technical person who asks for the strictest settings.
- **Recommend the phone checklist** at the end of the security step: Signal's Linked devices, Registration Lock and screen lock on their phone, her safety number marked as verified, and, when she has a number, the device with her SIM: a SIM PIN, a screen lock, hidden notifications and the carrier's port-out PIN.
- **Say plainly what stays a risk:** an unlocked phone or laptop with their Signal can talk to her (`/lock` from the phone stops her until `/unlock`), and root on the Mac reads everything. Tell them in these words: "Whoever has your unlocked phone ends any lock of your account, one sent from your laptop too, 10 minutes later at the earliest. With your phone gone, stop her on the Mac: `/usr/bin/sudo /usr/local/estia/bin/estia stop` (she starts again at the next restart of the Mac)."
- **What you see of a setup you started:** setup's step lines only, never an answer, a code, a PIN, a key, her number or an account ID; every answer is typed in the window, the Mac password only in macOS's box. **What is within your reach anyway:** you run as the person, so, before the move, the files setup writes as them (the answers file, the config, `web.env`, `tapo.env`, `calendar.env`) and the web keys' copies in their login keychain: never open them (rule 2).
- **Once she runs as `_estia`, AI sessions on this Mac, this one included, cannot read her data** or change her code or her programs without the person's password, as long as no admin rule skips that password (the security step removes one). Four limits stay; tell the person in these words: "even without such a rule, an admin sign-in lasts 5 minutes in its Terminal window, and each admin command starts them again: in that time every program in that window, one already running in it too, gets root without the password, so run her admin commands in a Terminal window of their own and end with `/usr/bin/sudo -k`", "a program of yours can catch your password with a fake `sudo` that your Terminal finds before the real one, so type `/usr/bin/sudo`; a fake one written into your shell's startup files runs even then, so `whence -va /usr/bin/sudo` must list only the file, never a shell function or an alias", "a program of yours can change what your next update puts live; the update shows the list of changes and the files they touch, not the code itself", and "while setup's window runs a step with admin rights, any program of yours can read or change what goes to that step, a key or PIN included, so close programs you do not trust while setup runs". What she sends to an Ollama that runs as the person (the Ollama app, an install from before 0.9.8 or without her own account) passes through their account: tell them so. Her own Ollama (a new install with her own account) runs as her. A copy a program made before the move still works.
- **Every update (`estia-deploy`) shows the list of changes and asks first:** have the person read the list before they say yes. A change to the tools root runs comes only with `/usr/bin/sudo /usr/local/estia/bin/estia-deploy --update-tools`, after its diff.

## Moving an older install

An install that already runs always on as the person (an older version) moves into her own macOS account the same way: `scripts/migrate-to-own-user.sh --dry-run` first, then `scripts/install-daemon.sh`. Two things differ: her voice service, when it runs, moves too; and within 7 days `/usr/bin/sudo /usr/local/estia/bin/estia rollback` goes back, with what she saved since. `/usr/bin/sudo /usr/local/estia/bin/estia remove-old` deletes her copies kept aside together with her old folders held for the rollback: no rollback after it. Do not suggest it within the 7 days unless they want the space back. setup_assistant.md, 2.7, has the details.

**Moving her to an account without a number** (her old number's account stays on this Mac as it was, unused: never unregistered, never deleted): the person makes the account on the Android phone (setup_assistant.md, 2.3, B, steps 1 to 4), then runs `/usr/bin/sudo /usr/local/estia/bin/estia signal-login` in their own Terminal window (`--dry-run` before `signal-login` first shows each step). It asks for the Account ID, the Recovery key and her username, as setup does, stops her for the move and switches her config; it starts her again only when she was running before it; a step that fails switches nothing. Then they text her username from their phone, and her doctor shows Signal account ✓. Then tell them, in these words: "Her old number's Registration Lock lapses after 7 days offline: whoever gets that number next can write to you from her old chat. Delete or block that chat on your phone and never trust it again; keep the SIM if you can." On an install from before, the update order first: the deploy, then `--update-tools`, then the deploy again.

**The order that worked** (a Mac reached over SSH):

1. The dry run (`scripts/migrate-to-own-user.sh --dry-run`), then the move.
2. With calls set up, wait for her text "My voice is ready: you can call me now." (up to about 15 minutes: the Neural Engine compiles her voice again for her own macOS account), then a text and a call; with voice but without calls, go on once the person's `/usr/bin/sudo /usr/local/estia/bin/estia check` shows `stt` and `tts` ready on its `voice:` line (her voice service answers only programs running as her own macOS account: a `curl` of yours is refused); without voice, go on at once.
3. The person runs `scripts/harden.sh` in their own Terminal, with a second SSH session open.
4. Test a new SSH login from the laptop and a call; after `scripts/harden.sh --nuclear`, also the programs on the Mac the person opens from the laptop (the firewall).

## If something fails

- **The doctor says what to do** (`/usr/bin/sudo /usr/local/estia/bin/estia doctor`, run by the person; `scripts/doctor.sh` before her own macOS account). Every ✗ line ends with the command that fixes it, or the log to read first. ○ means set up, not used yet: that is fine. A ✗ "failing since …" is the part's last real use: after a fix, have the person use the part once, then run the doctor again; never the same fix twice. For her log, the person runs `/usr/bin/sudo /usr/local/estia/bin/estia logs bridge -n 40` in their own Terminal window and shares what it prints (only what happened and when, never message text).
- **Setup stopped** (a run you started): its ✗ line names where and why ("the window shows why": the window's stop screen has the step's own ✗ line and its fix); every answer is kept: say the fix, then start setup again. "The Estia Setup window was closed": start it again when they are ready. "an error in its own code": start it again; if it comes back, report it (SECURITY.md says where). In a Terminal run: "not a git clone" (1); a stopped download (setup again resumes it).
- **Ollama stopped setup:** with her own Ollama (a new install with her own account) nothing else on the Mac stops setup; what does, before anything downloads, each line with its fix: another program on port 8151, too little free disk, a folder on the way that an account other than root can change, or her account that could not be made (start setup again: at "Kept from your last run", Change beside Always on, then No; in their own Terminal window, `scripts/setup.sh --redo move`, answer No). Never tell the person to quit or delete another Ollama: it stays beside hers. Without her own account (not recommended): the checks from before 0.9.8 run, and Homebrew's Ollama, or the Ollama app with the background build chosen, stops setup with the fix it names; recommend her own account instead. A download that did not check out installs nothing: setup again, and if it says the same, SECURITY.md says where to report it. `scripts/install-ollama.sh` started by you stops at once: it asks for admin rights only in Terminal; setup's own Ollama step asks in its window.
- **"✗ Always on: the move did not finish"** (setup stops before the security step): ask for the ✗ line in the window, fix that, `scripts/migrate-to-own-user.sh --dry-run`, then setup again; on a new install nothing was installed.
- **Signal registration failed:** each try needs a new captcha link; a number or a link that does not fit is asked again, with what is wrong. An account without a number: the Account ID and the Recovery key from their password manager, typed again; never ask for either in chat. **The one-time word did not arrive:** most often it went to their own number or Note to Self instead of her new number or her username; setup goes on looking by itself.
- **Doctor's Always on line shows ✗** ("installed, no sign of life for 12 min", "restarting, last exit code 1", "installed, stopped" or "installed, not loaded: launchd does not run it"): have the person run the command doctor prints below that line and share what the log says. Doctor only reads; it never restarts her. A ○ "installed; whether it runs could not be read": her log says more.
- **"! YouTube: the YouTube helper is not set up" or "the documents helper is not built":** before her own macOS account, `cd tools/youtube && uv sync --frozen` (no admin rights); in her own macOS account, the person's next `/usr/bin/sudo /usr/local/estia/bin/estia-deploy` builds them, after `/usr/bin/sudo /usr/local/estia/bin/estia-deploy --update-tools` when it says the root-run tools differ.
- **"✗ Documents":** "not shared with her", "no share token" or "no folder": `scripts/share-documents.sh`. "… is not your ~/Estia-KB: the share opens only ~/Estia-KB to her": the person sets `folder = "/Users/<them>/Estia-KB"` (6, her config), restarts her and moves any PDFs over in Finder. "…/.git is not yours (her account may have added it)" or "holds a git checkout": tell the person, and change nothing yourself. "macOS refuses it (operation not permitted)": the folder is in Documents, Desktop or Downloads; `~/Estia-KB` is the fix.
- **Her voice is silent on a call, or her answers come as texts:** Pocket TTS is her only voice: a line it cannot say is said by no other voice, so a voice note's answer comes as text alone, and on a call the rest of that answer comes as a Signal text. Korean, Polish, Russian and Japanese have no voice: her answers in them come as text, and calls in them are not picked up. Doctor's "Pocket TTS voices" line says why (not fetched yet, loading, unavailable, files changed) and its fix; to see more, the person runs `/usr/bin/sudo /usr/local/estia/bin/estia logs voice -n 40` in their own Terminal window (read-only) and shares its "did not say this line" lines, which name the reason. Nothing is fixed by hand but what doctor's fix names. A config from before 3 Nov 2026 that names a Kokoro voice (such as af_heart) still loads, as heart or michael, and her log says so once at each start.
- **No reply, no welcome, no answer to a call:** `/usr/bin/sudo /usr/local/estia/bin/estia check` shows whether her service and signal-cli run; `ignored a message from <ACI>` in her log is an account that isn't allowed. Calls go unanswered while her voice loads (up to about 15 minutes after an install, a move or a macOS update); with calls set up she then texts "My voice is ready: you can call me now."
- **Anything else** (the firewall, a cloud model, a held device): the doctor's line has the fix. `setup_assistant.md` is the full guide, and section 8 explains the security model.
