# Public docs, the website's quotes and releases

## Commands

- Release notes: a tag's section of `CHANGELOG.md`, published word for word by `.github/workflows/release.yml`, inside the fixed page `.github/release-page.md` (the tagline, then "What changed in {{VERSION}}" with the section at `{{SECTION}}`; owner, 18 Oct; no list of what is in 0.9 since 0.9.5, owner, 19 Oct). Before tagging vX.Y.Z: rename `## [Unreleased]` to `## [X.Y.Z] - YYYY-MM-DD`, put an empty `## [Unreleased]` above it, and at the end move the `[Unreleased]` link to `compare/vX.Y.Z...HEAD` and add `[X.Y.Z]: …/compare/v<previous>...vX.Y.Z` (`tests/test_docs.py` checks each link); a tag without its section stops the workflow before anything is published (`tests/test_docs.py` runs the step with a gh stub). The workflow reads `CHANGELOG.md` as the tag has it: a section added after tagging needs the tag moved

- Known security holes (owner, 23 Oct): before tagging, `scripts/vuln-scan.sh --download` (a fresh OSV database into `~/.cache/osv-scanner`, then osv-scanner offline over `uv.lock` and every `tools/*/uv.lock`): a hit blocks the release until that package is updated to its fixed version and the scan is clean; `scripts/verify.sh` runs the same scan offline (`--if-ready`: one "not checked" line without osv-scanner or its database), and `.github/workflows/osv-scan.yml` runs it on GitHub at every push and every Monday (google/osv-scanner-action pinned by its commit, read-only); `release.yml` calls it on the tag before it publishes (its `scan` job; the publishing job `needs: scan` and runs only `gh`; review X6, 0.9.7), so a known hole stops the release on GitHub too. The pass line names the offline database's day, and a line warns when it is over 3 days old. Not scanned: the Swift packages (`tools/voice/Package.resolved`, checked by hand at each release), Python itself (deploy's `uv python install`), Ollama (`scripts/install-ollama.sh`), the JVM signal-cli and the call helper (`tools/call-tunnel/`), Homebrew's programs (kept current by Homebrew); GitHub pauses the weekly scan after 60 days without a change to the public repository (re-enable it under Actions). `tests/test_vuln_scan.py` checks the script, verify's line, this step and the workflow
- Signal's key symbols (owner, 25 Oct: "Signal might add more non-alphanumeric characters"): before tagging, compare `hostsec.KEY_SYMBOLS` with `CHARACTER_DISPLAY_MAP` in Signal-Android's current `core/models-jvm/src/main/java/org/signal/core/models/AccountEntropyPool.kt`: `gh api repos/signalapp/Signal-Android/contents/core/models-jvm/src/main/java/org/signal/core/models/AccountEntropyPool.kt --jq .content | base64 -d | grep -A4 'CHARACTER_DISPLAY_MAP:'`. A new pair goes into `KEY_SYMBOLS` (shown symbol to stored character, in lower case) with a test, its source link moves to the commit checked, and the words that list the symbols name it (`KEY_LEFT_OUT`, `KEY_STRAY`, `KEY_SEPARATOR`, setup_assistant.md 2.3, SETUP-WITH-YOUR-AI.md); until then a key with that symbol is refused and named, never guessed. Signal's own reader drops a symbol it does not know; signal-cli's copy may lag, which is harmless, as it gets only the stored form
- Signal's own words in the phone's steps (owner, 28 Oct: "Signal Account" in our words, Signal names it Signal Login; the route's label, where setup first names it, says "a Signal Account / Login", `prompts.SETUP_ROUTE_NO_NUMBER`): before tagging, check that Signal-Android still shows "Register without number", a purchase screen titled "Signal Login" and its "Pay" button: `gh api repos/signalapp/Signal-Android/contents/feature/registration/src/main/res/values/strings.xml -H 'Accept: application/vnd.github.raw' | grep -E 'register_without_number|SignalLoginPaymentScreen__(signal_login|pay_s)"'`. A change goes into `hostsec.NUMBERLESS_STEPS` (and its bold words in `setup_signal.NUMBERLESS_STEPS`), setup_assistant.md 2.3 B and SETUP-WITH-YOUR-AI.md, its source link moving to the commit checked (tests/test_setup_bold.py pins the step).
- Setup's gum (`setup_gum`): before tagging, compare `VERSION` with charmbracelet/gum's latest release; a newer one is taken only with a release, its tarball's sha256 from the release's checksums.txt and the program's from that checked tarball, then `GUM_REAL=1 GUM_PROGRAM=<the new gum> uv run pytest tests/test_setup_faces.py -k every_flag` (every flag setup gives gum is in its own --help) and THIRD_PARTY_NOTICES.md's line.
- Dependency updates: a version under 7 days old only when it is the official maintainers' fix for a known hole (owner, 23 Oct); a new version comes only with a release, after the tests (no update installs itself); Python's patch version is the exception, as deploy's `uv python install 3.13` takes the newest 3.13 the installed uv knows (review of 0.9.7, X4: SECURITY.md says so)

## Gotchas

- The website (estia.one, its own repo) checks README.md and GUIDE.md with drift tests (`tests/drift.test.mjs`, `ESTIA_REPO=<checkout>`) that read some README.md or GUIDE.md, SECURITY.md and setup_assistant.md sentences word for word (`tests/test_docs.py` pins every one in `SITE_README` (in README.md or GUIDE.md: a pinned sentence may move between the two), `SITE_SECURITY`, `SITE_SETUP`, `SITE_AGENTS` and `SITE_PROMPTS` (a prompt line the site quotes: a prompt change tells the site too), with her commands, the slash commands and the languages the page names; `site_misses`): a changed one turns the site's tests red until the site matches, so change the pin on purpose and name every changed one (old and new) for the site. README.md is the front page (under 120 lines); GUIDE.md holds the rest, and the site's guide page renders it as written: no HTML (a tag shows as text), no image (it becomes a link), no http:// link, every #link a heading of GUIDE.md (GitHub's anchors: -1, -2 for a repeated heading), one H1, and an `sh` fence holds only commands, one per line (`tests/test_docs.py` checks each).
