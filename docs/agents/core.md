# Core: the bridge, its store, config and status

## What Estia is

Private assistant **Estia** (every install names its own: the config's `name`) on the local Gemma model (`local-worker`, an Ollama alias; see setup_assistant.md, "Model (once)"), reached over Signal. In code and docs "Gemma" means the model; the assistant's name (rules, greetings, notes, labels) is the config's `name` (default "Estia", `config.DEFAULT_NAME`): prompts take it at runtime (a `name` argument, a `{name}` template, `<name>` in the rules), never a constant. One Python process (the bridge) runs `signal-cli jsonRpc` as a child, answers the allowed user with Gemma and its tools (memory, links (a YouTube link: its captions), host status, projects (an extra, off without `[projects]`), documents (an extra, off without `[documents]`: the PDFs in the owner's `~/Estia-KB` and the ones the user sends), chords (an extra, off without `[chords]`: transposing, a capo, a chord's notes and the key of given chords, worked out by code, given in code's note), mail, calendar, web search, lights and plugs, Spotify, calls, reminders; photos and voice notes as input), sends a morning digest (calendar, then mail) and the reminders the user set (a text, and a Signal call for a wake-up call), now and then writes first (messages she starts herself, gated by code; the evening note, code's three questions at the user's time, off by default), keeps memory in one SQLite database, and runs always-on as LaunchDaemon `com.local-assistant.bridge`. Full explanation: `setup_assistant.md`.

## Layout

- `config` (private TOML; `bot_number` is her number or the Account ID of an account without a number, kept in lower case; `default_avatar`: Estia's mark (Hearth, `docs/brand/estia-avatar.png`; owner, 25 Oct: "just the mark, no letters at all"). Her Signal picture is Estia's mark, whatever her name: a silver ring around an orange rounded square. The letter pictures a name other than Estia got from 15 to 25 Oct are gone, and an `avatar` that still names one (`is_old_letter`: a.png to z.png in a `docs/brand/letters` folder, a checkout's or a release's) gets the mark, never a missing file; with `avatar` left out or naming one, the next start sends the mark, as the stored digest differs. Known gaps, by design: a letter the move copied into her config folder (her `avatar.png`, `ownuser._copy_avatar` has no letter check) is her own picture to the bridge and stays; `avatar = ""` sends nothing, so Signal keeps the letter)
- `store` (SQLite schema, FTS5 search, migrations)
- `gate` (classify Signal envelopes; a PDF by its type: `Kind.DOCUMENT`, its file name kept; the user's words and a caption as their app showed them, `shown_words`: a spoiler range, signal-cli's `textStyles` in UTF-16 units, becomes `HIDDEN_MARK`, "(hidden part left out)", and tag characters (an emoji flag's own kept) and bidi overrides, embeddings and isolates are removed, so text the user may never have seen, a forwarded message's hidden part, is never their own words; second review of 0.9.8, redteam-01; unchecked: whether Signal's forward keeps a spoiler, and whether Gemma 4 reads tag characters)
- `gemma` (Ollama client, retries, cancellation; every request names `top_p` 0.95 (`TOP_P`, Google's setting for Gemma 4: Ollama's OpenAI layer sends 1.0 for a request that names none, over the model's own 0.95; it has no `top_k` field, so the model's 64 applies); `ModelPin` and `PinnedGemma`: the model alias against Ollama's own entry for it, `ModelEntry`, never a cloud model, and against `model_digest`)
- `commands` (slash commands; `/tools`: her tools' list, `StatusHost.inventory`, in `prompts.inventory_text`'s words; `Guard`: the user's devices, held or allowed, and the lock)
- `watchers` (scheduler for checks without Gemma, alert state; in quiet hours, the initiative's or 22:00-08:00, an alert and a recovery wait for their end and a problem that came and went is one morning line, kept in the state table and cleared kind by kind once its message was sent or stored as failed (the App's send never raises: a failed one is sent again within the recovery window, `Lifecycle.resend_failed`; review I4); security notes never pass through it)
- `health` (host checks, `extra_checks`, `mini_status`; an http check's JSON `status` reaches her only as a short word, `_STATUS_WORD`, any other as "not ready": review G8, a service that echoes could plant text there)
- `photos` (file type, `sips` conversion; `ShownPhoto`, the last photo for follow-ups)
- `keyfile` (the 0600 key file)
- `part_status` (each part's last real read or call in `status.json`; the three states doctor and /status show, and a warning beside them ("!", `warn` and `unwarn`: the part works but not all of it, kept from its first time through reads that work; ✗ shows over it; documents' `ocr_unavailable`); its `security` section: a changed safety number, her account's device count, the model's pause and a cloud model's, as times and a count)
- `app` (wiring, the queue, envelopes, `process`, delivery, voice notes, the lock, the model pin, logs, main; since 0.9.5 the call side is `call_host.CallHost`, the documents side `documents_host.DocumentsHost`, start-up, recovery, the welcome, sweeping and retention `lifecycle.Lifecycle`, and status, `capability_lines`, the alerts (`StatusHost.alert`, `App._alert` its delegate) and the security and device loops `status_host.StatusHost`, and (0.9.7) her Signal account's state `signal_host.SignalHost` (the accounts whose safety number changed, signal-cli's connection, Signal's wait, the stored messages of an account no longer allowed), each built by `App` with a back-reference (`self.app`), `App` keeping one-line delegates for the names tests call; `GLANCE_WAIT_SECONDS`, `WARM_UP_SECONDS`, `WARM_UP_GLANCE_SECONDS` and `DOCUMENTS_FIRST_SECONDS` stay in app.py, which tests patch, and are given to the hosts when built; before: wiring, queue, recovery, `capability_lines` (the list's current values: `/voice`, `[calls] interrupt`, `/initiative`, the projects' levels, the documents folder (`documents.shown_folder`: one in the owner's home as `~/…`, only with `[documents]`), the Mac's security level read every 4 hours as doctor reads it, `hostsec.mac_security_level`, live Mac only; a change rebuilds her rules), the welcome, the lock and held devices at envelope time, receive problems, the device count, the model pin, retention, logs bounded in-process, main)

## Rules

- Photos live only until answered (follow-ups within 5 minutes of the start of its answer reuse the last photo from memory, never from disk; `photos.ShownPhoto` keeps it; a reminder in such a follow-up goes as after outside text, never in the photo's own message: `memory-initiative.md`, owner 28 Oct, review of 0.9.8, memory-2): signal-cli's copy is deleted afterwards, strangers' and unsupported files at once; a PDF or text file from the allowed user is saved into the documents folder (with `[documents]`; without it, a file she cannot open), then signal-cli's copy is deleted; other downloads (link previews, quote thumbnails, avatars, edited messages) are swept once 10 minutes old.
- The user's devices (`commands.Guard`, table `known_devices`, `messages.source_device`: schema v9, on top of /babble's v8): device 1 (the phone the account was registered on) of every allowed ACI is known from the start; a message from any other device (or one Signal does not name) is held at envelope time: not stored, not read, no receipt, its files deleted at once, and a code note (`prompts.DEVICE_HELD`, at most once an hour per device, also while locked) goes to the account, so the phone sees it, and is kept as a sent note once delivered (`Lifecycle.keep_sent`: in her history, so she knows a message was held). `/devices` lists them; `/devices ok N` allows a held device, only from a device she already answers. Signal gives a new linked device the lowest free number from 2, so a number is not a device: an allowed device silent for `TRUST_DAYS` (14; `last_seen`, `Guard.seen` on every message it sends) is held again (`DEVICE_HELD_SILENT`), and `/devices forget N` (from a known device, never the phone) removes one. Calls name no device: a call from a new linked device still rings.
- `/lock` (typed, from a device she answers; at envelope time, never behind an answer in the queue) stops everything until `/unlock` from the same device, `UNLOCK_WAIT_SECONDS` (10 minutes) later at the earliest: state `lock:on`, `lock:device`, `lock:since` (survives a restart, no sudo). While locked: incoming messages are not stored or read and get no receipt; `_send` sets every outgoing message `ignored` (never sent later; recovery never resends it), voice answers and the welcome wait; an answer already on its way stops: no tool call and no request to Gemma after the lock (`Brain(stopped=…)` raises `LockedError` before each; the message `ignored`), its voice note made meanwhile is not sent, and a call the lock ended gets no summary (review I1); a running call is hung up, and so are a call she is placing (still ringing, or picked up as the lock came: `_locked_dial`, a failed call) and the allowed user's call she lets ring before answering (`answer_after_s`); a call that rings while locked is ignored, never rejected, also one whose ring came just before, while her voice's health was read (`CallManager(locked=…)`, checked again after the voice's health and the rings; review C1); reminders wait (`ReminderScheduler(locked=…)`: nothing fires, retries too) and come after `/unlock` (a text one more than `ON_TIME_S` late as `prompts.REMINDER_NOTE_LATE`, with the time it was due; review O4), a call reminder due meanwhile as its text only ("No call: I was locked (/lock)."); the reminders' start-up check after a restart waits for `/unlock`; messages she starts herself are skipped with the reason `locked` (waits like `/quiet`; Gemma is not asked, the calendar not read); language practice gets no answers and its recap waits for `/unlock` (see Language practice). `/lock` and `/unlock` replies go out at once, in code's words, never stored.
- `/lock`'s "see Language practice": that rule is in `docs/agents/languages.md`.
- The model always runs on the Mac: a model name whose tag ends in `-cloud` or `:cloud` (an Ollama cloud model: it runs on Ollama's servers) is a config error (`config.is_cloud_model`), and the bridge always reads the alias's entry in `/api/tags` (`OllamaGemma.model_entry`, `app.model_pin`, with or without `model_digest`) at the start, every 5 minutes and before every chat (`ModelPin.ensure`: one local request, no grace period): an entry with `remote_host` or `remote_model` (Ollama 0.40.0's marks of a cloud model; `gemma.is_remote`) pauses every Gemma call like the digest below (`ModelPin.why == "cloud"`; code's notes `prompts.MODEL_CLOUD` and `MODEL_CLOUD_RESUMED`, spoken `MODEL_CLOUD_SPOKEN`; `security.model_cloud` in `status.json`), and doctor's Model line is ✗ with the fix. The terminal draft (`initiative --draft`) checks the same before it asks the model. The model's pin: with `model_digest` (64 hex digits, "sha256:" optional) the alias's digest from `/api/tags` is compared at the same reads; any other digest (or the alias gone) pauses every Gemma call (a model swapped in between a read and its chat still gets that chat; the owner's account, which runs Ollama, is outside the pin) (`PinnedGemma` raises `ModelPausedError`): a message gets code's note (`prompts.MODEL_PAUSED`), never a Gemma answer, the pause and its end are one note each, and `status.json` keeps `security.model_paused`. An entry that cannot be read changes nothing (the next chat reads it again). The evals hold to the same: `EVAL_MODEL` and `EVAL_BASE_URL` are refused for a cloud name or a host off the Mac, and `run_cases` stops before any case when Ollama lists a cloud model. Without `model_digest` only a cloud model pauses, and doctor shows ! with the line to pin. AgentJev's Host and Origin check lives in its own repo (SECURITY.md, known gaps).
- History retention: `[privacy] keep_days` (left out: kept, as before) deletes messages, pages and tool calls older than that with their FTS rows (`Store.prune`, then each index's `optimize`), once a night between 03:00 and 05:00 when nothing else runs (state `privacy:pruned_at`), then `Store.compact` (checkpoint, VACUUM, checkpoint; it blocks the database for a moment). Open reminders and open check-ins are never touched (their messages stay); her own messages go like the rest (review I27: they stayed a year), the initiative log keeping its row without the message; the profile stays, its links to deleted messages and pages are cleared; an ended conversation without messages goes with its summary. An open conversation whose deleted rows showed outside text keeps that mark (state `outside_seen:<id>`, `Store._keep_outside_seen`; review I8: the guards after outside text ended silently while the summary kept its residue), until `/new` ends it; the next prune drops an ended one's mark. A trim that takes such a turn out of the window without a summary (the emergency one, or `_fit` to the model's context) sets the same mark (`Store.move_window_start`): her later replies in the window may repeat it. `PRAGMA secure_delete = ON` in `Store.open` overwrites deleted rows in the file.
- Logs are bounded in-process, never by newsyslog or root: `bridge.log` is a `RotatingFileHandler` (10 MB x 5 older files), `launchd.log` (the bridge's stdout and stderr, in `/var/log/estia`) is emptied when over 10 MB at the start and before any write (`app.cap_streams`), and so is `voice.log` (`LogCap` in VoiceCore); every file is private (umask 077).
- Each answer's model line (owner's call, 22 Oct: two turns of 20 s logged only "0 tool calls"): "message N answered", "call turn N answered" and "practice call turn N answered" end with `; model: ` and `Reply.timing.line()` (`gemma.Timing`: the answer's requests, the largest prompt, the prompt tokens Ollama read anew (`usage.prompt_tokens_details.cached_tokens`), its prompt eval and generation times (a stream's `timings`), the tokens generated, the bridge's total, and the rest as "waiting or loading"; each part only when Ollama sent it). Requests are streamed with `stream_options.include_usage` for that reason (Ollama 0.40.4 times only a stream's last chunk, `middleware/openai.go`); the answer is still read whole (`gemma.parse_stream`: a tool call in pieces joined, none kept when no tools were offered, as unstreamed), an unstreamed JSON answer is read as before, and a stream cut off before `[DONE]` is tried again like an HTTP 500. Found with Ollama's own log (`prefix_cache.go` "cache hit" lines, metadata): turn 998 had 4 of 17,213 prompt tokens cached (13.5 s to read, then 7 s to generate), turn 1000 none of 17,442 after 4.6 s in the queue (14.1 s to read, 3 s to generate); another program's requests on the same Ollama, a workflow's evals at about 7,500 tokens every 7 s, had taken the prompt cache between turns and queued hers (turn 994 waited about 6 s behind one). With nothing else between them her turns found their prefix cached (turns 994 and 1002: 16,558 of 17,026 and 16,772 of 17,558).
- `status.json` (part_status) holds part names, times, fixed reasons and HTTP status numbers only: never message, mail, event, search or device text, addresses or keys. Recording never raises into the part it watches.
- The welcome (`prompts.welcome`) is written by code and starts only when the store has no messages at all (a fresh install; an update never sends it). It is owed once to each ACI allowed at that start (`welcome_owed`, then `welcome_sent` in `state`); an ACI allowed later never gets it. It is stored only after it was delivered, as a sent note, so recovery never sends it again (in her history as code's note, `code_notes`); an ACI it could not reach gets it at the next start.
- Health checks and git run fixed commands from code: that rule, with the project name matching, is in `docs/agents/documents-projects.md`.

## Gotchas

- A note sent before `recover()` (at the start) goes out twice: recovery resends every pending outgoing message of the last 10 minutes. Start-time notes (the model's pause) are sent after recovery.
- `status.json` is written whole: `PartStatus` keeps the `security` section beside the parts, so one writer never drops the other's facts.
- signal-cli always names the sending device (`sourceDevice`); a test envelope without it is held (the fake signal-cli adds device 1, as signal-cli does, when a test leaves it out). A `Decision` rebuilt in the app must keep its `device`.
- An older release on a newer database: the schema only moves forward, and older code reads the rows it does not know. A release from before the evening note (v11) put back by a deploy's rollback or deployed from an older commit raises KeyError 'evening' in `/status` and doctor (`prompts.INITIATIVE_KINDS[kind]`) for 4 weeks after an evening note was skipped or failed while the initiative is on, and counts sent evening notes toward `max_per_day` (setup_assistant.md, Updates: a known gap). Keep a new kind's rows where older code never reads them, or say the limit. A release from before the two parts (v13) reads both as one 6,000-character profile: its consolidation and learning may delete facts to fit (setup_assistant.md, `profile_facts`: no "remember" until the next deploy).
- `sqlite3 -readonly` cannot open the WAL database while the bridge is stopped (no `-shm` file).
- `sips -Z N` also enlarges smaller images: read the size first (`photos.prepare` does).
- `recover` sets aside (`ignored`, its files deleted) every stored unanswered message from an account no longer in `allowed_acis`, as `process` does first (review S3: one taken out in a hurry, a stolen phone, still reached Gemma after the restart; only the reply was refused). An `ignored` incoming message (that one, or one that came in before `/lock`) is never read for her: `Store` leaves it out of her window, idle learning, the check-ins and her history search with its neighbours (`store._NOT_IGNORED`). It resends outgoing messages that are `pending` or `failed` (within 10 minutes), and while the bridge runs `Lifecycle.resend_failed` sends the `failed` ones again every `RESEND_SECONDS` (60 s) within the same window (during a call it waits for its end, as every text does), never to an account no longer allowed or whose safety number changed, and never a firing reminder's note (the reminders' own retry, every 5 minutes for an hour, sends it) (review I4; `_send` says whether a message went out and never sends one already `sent` or `ignored`, `StatusHost.alert` logs "alert sent" only then, and `_deliver` waits no more after its third try). signal-cli's JSON-RPC errors -5 (Signal's rate limit: `RateLimitError`, `retryAfterSeconds` and a challenge token from the send's results, the token never logged) and -6 (a captcha refused: `CaptchaRejectedError`) are typed in `signal_io`; `SignalError.wait` is the pause before the next try: a rate limit of at most `RATE_LIMIT_WAIT_S` (10 s) is waited out, a longer one, a captcha asked for (lifted by a solved captcha or after Signal's wait: one log line with that wait, naming setup_assistant.md, Operations; solving it is not built in) or one refused is no try now. A longer rate limit or a captcha asked for is kept as Signal's time (`SignalHost.wait_after`: `retryAfterSeconds`, `LIMIT_UNNAMED_SECONDS` without one, at most `LIMIT_MAX_SECONDS`) in status.json (`security.limited_until`, `limited_captcha`), also across a restart: `_deliver` tries nothing until then (`SignalHost.waits`; review S4: the resend pass sent every failed message again every minute), and doctor's "Signal limit" ✗ names the time ("nothing is sent until then", never "her messages wait": a reply older than the 10-minute window by then is never sent; a captcha solved by hand does not end the wait sooner, as the bridge cannot tell). No /status line: its answer waits too. `/lock` hangs up before its reply goes out, so a waiting send never holds the hang-up back. The morning digest waits while locked or during a call (`MorningDigest(held=…)`: nothing composed, the day not marked, until noon), and the note on new documents for a call that began during the look (review I5). A note that must never go out again (a reminder note that may have gone out, one given up on, the busy note that could not go out: `App._send(once=True)`, review S19) is set to `ignored`, not `failed`.
- A setting that names a file the user may move, replace or delete (the `avatar` picture) is checked where it is used, never at load: a `ConfigError` stops the always-on bridge (launchd restarts it every 30 s, offline, with no way to say why over Signal). Only the setting's form is a config error; a file that cannot be used is a logged skip and a doctor warning.
