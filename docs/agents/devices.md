# Lights and plugs (Kasa, Tapo, Hue)

## Layout

- `devices` (lights and plugs: names, rules, confirmation, helper calls, notes; a Hue light by the bridge's light id, `hue-set`, and every Hue light's status in one `hue-status` run)
- `tools/tapo/`: the device helper (python-kasa in its own uv environment; the bridge runs it per command), with `hue.py` (standard library: the Hue Bridge over HTTPS, CLIP API v2, its certificate pinned; pairing and the lights' list).

## Commands

- Device helper: `cd tools/tapo && uv run pytest -q && uv run mypy`; list the devices on the network: `scripts/tapo-discover.sh` (read-only; with `hue.env`, also the Hue Bridge's lights); pair the Hue Bridge: `scripts/hue-pair.sh [address]` (press its button when asked; in her own user it runs as her: `/usr/bin/sudo /usr/local/estia/bin/estia hue-pair [address]`)

## Rules

- Lights and plugs: only devices in `[[tapo.devices]]` (private addresses), by name; the bridge runs the helper with fixed arguments (no shell) and never holds the TP-Link login (only the helper reads `tapo.env`); "ask first" runs only on the user's own yes and "never off" is refused, both in code; a change in an answer whose message is not about devices (no device word or name, see `Devices.about_devices`) also waits for the user's yes, so a line planted in an earlier page cannot act on a later "thanks!"; while outside text from an earlier answer is in her context (`Turn.after_outside`) or a note quoting it, a device the message does not name (`Devices.named_by`) waits too, and the waiting call is logged with `tools.REFUSED_ARGUMENTS` (review G2: "no, turn off the bedroom light" is about devices and switched the lamp an audio file asked for); what really changed is a code-written note, also for a change already on its way when its task is cancelled (a call hung up, a turn over its time: `Devices._execute` finishes it within the helper's time limit, then the note and `recently_switched`; review I13), and a cancelled status read stops its helper; an answer that claims a change (switched, dimmed or set; English first, `claims.switch_clauses`: never a state report, a question, an offer, a promise or a gerund with a verb of its own ("turning off the lights before bed helps", "turning it off would need your yes"); "is now on" and "has been switched off" count only without a `device_status` in the answer) of a device no `device_set` in it changed gets code's note `prompts.DEVICE_GUARD`, "Nothing was switched." (`DEVICE_GUARD_ELSE`, "Nothing else was switched.", when the answer switched another one; `Reply.device`, said on a call too; in her history only as code's note). Per claiming clause (`Devices.unmade`): one that names music, Spotify, a speaker or the volume is never flagged; one that names devices by their whole name needs each of them in `Turn.switched`; one with only a device word, or only "it" after a message about a device, needs any; a clause about an earlier switch ("ago", "earlier", "already") also counts what a confirmed change reached in the last 24 hours (`Devices.recently_switched`, in memory, a yes's too). Philips Hue lights (owner, 14 Oct): `brand = "hue"` and `light = "<CLIP v2 id>"` (no `host`) in the same `[[tapo.devices]]`, with the same rules, about-devices check, yes and notes; on, off, brightness and the whites, a colour refused in code (`_HUE_WHITES`). Only through the Hue Bridge at its private address, never Philips' cloud (no discovery.meethue.com, no remote API): `hue.env` (0600: `HUE_BRIDGE`, `HUE_KEY`, `HUE_FINGERPRINT`) is read only by the helper, never by the bridge process; the key goes only in the `hue-application-key` header (never argv, output or logs; `Pairing`'s repr leaves it out). Every connection compares the certificate's SHA-256 with the pinned one before anything is sent (`hue.exchange`), nothing on a mismatch (`certificate`); a connection never reopens itself (`_Tls`: `auto_open = 0`, so http.client cannot reconnect past the check). A status read takes two requests whatever the number of lights (`hue.statuses`: every light, then every `zigbee_connectivity`; `hue-status <id> …`, one helper run from `Devices._ask_each`): a light whose device's link is not "connected" is `unreachable`, never its last known state (the bridge answers a read of a light off at the wall with that); no link entry, or an unreadable list, reads as before. A change is read back once more after `SETTLE_SECONDS` when the read-back does not show it yet, then reported as sent (the PUT had no error); untested whether a real bridge needs it. Pairing (`hue.py pair`, `scripts/hue-pair.sh`): `dns-sd` -B, -L, -G v4 with a time limit each, private addresses only; the first certificate is trusted and shown (TOFU) and pinned for the rest of the pairing; POST /api with `generateclientkey` until the button (101), the client key not kept; an answer that is not a Hue Bridge's (not JSON, not CLIP's list) stops it at once ("answers, but not as a Hue Bridge"), no answer is asked again and, at the deadline, "No answer from the bridge", never the button. The helper's Hue codes: `not_paired`, `key`, `certificate` (shared: they fail the part like the TP-Link login, noted once per brand until that brand works: `Devices._noted`), `no_light` (one device), `unreachable`, and `invalid` (a change the light cannot make, its fixed why in the note, a Hue White bulb and a white); part reasons `not_paired`, `hue_key`, `certificate`, `no_light`. Doctor's Hue Bridge line runs the helper's read-only `hue-check` (never under a test's root): ! names a light the bridge cannot reach (`disconnected`). The list of what she can do names each brand once, in config order (`DeviceSpec.service`: "TP-Link" for brand `kasa`, which covers Kasa and Tapo, so a Tapo plug never reads as not set up; "Philips Hue"), as the calendar line names its services; the Hue clause (`prompts.CAPABILITY_HUE`) appears only with Hue lights (eval `hue_no_colours`: only its harness has a Hue light, `Case(hue=True)`, so no other case's request has the Hue clause).

## Gotchas

- `python -I` leaves the script's own folder off `sys.path`: a helper the bridge runs that way is either one file (`tools/ical`, `tools/youtube`) or adds its own folder itself (`tools/tapo/helper.py` for `hue.py`; `test_the_helper_runs_hue_actions_in_isolated_mode` runs it isolated). Otherwise its imports fail live while its tests pass.
- Only Kasa devices are tested: older ones speak the local protocol without a login, newer Kasa firmware (KLAP) needs the TP-Link login. Tapo devices go through the same library with that login but are untested; Tapo firmware with the TPAP login is not supported by python-kasa 0.11.0.1 (the helper says "unsupported", the device's login in its detail; one it refused to send the login to, AES login v1 or over HTTPS, is marked `"refused": true`, and `devices._unsupported` names only a login code knows). The `tapo` names in paths and config keys cover Kasa too, and Hue (`tools/tapo/`, `[[tapo.devices]]`). Hue lights are untested on a real bridge (CLIP v2: the square bridge or the Bridge Pro, never the first round one): the tests' CLIP v2 answers follow Philips' published shapes, the `dns-sd` output the format macOS 27 printed for another service; pairing, a light's answer and a certificate after a bridge firmware update need the live test.
- macOS's `dns-sd` never exits on its own: every run has a time limit (`hue.run_for`: TERM, then KILL); it prints a found service at once even into a pipe, but nothing at all when nothing is found.
